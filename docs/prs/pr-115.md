## Summary
First root cause of the agent's native working-set growth (handoff `docs/development/handoffs/2026-09-26-agent-native-memory-leak.md`).

`safeVariantClear` (`internal/agent/wmi/connection.go`) returned early for any `VT > 0x1000`. Every SAFEARRAY variant (`VT_ARRAY|elem`, e.g. `0x2008` for `string[]`) is above that, so `VariantClear` never ran for array-valued WMI properties. The SAFEARRAY descriptor, its data and every element BSTR leaked on each read.

- The guard is from the initial import (fe74044), but nothing read arrays until the 2026-08-22 collectors. That matches "flat for 37 days before August".
- **Per-cycle sources:**
  - `firewallRules`, every 5 min: `LocalPort`/`RemotePort` on `MSFT_NetProtocolPortFilter` and `LocalAddress`/`RemoteAddress` on `MSFT_NetAddressFilter`, about 4 arrays per rule. The laptop has 696 rules, the VM 468.
  - `defenderState`, every 2 min: list-valued `MSFT_MpPreference` properties.
  - `hostPosture`: the `Win32_DeviceGuard` service lists.
- **Fix:** skip only by-reference variants (they don't own their target) and clear everything else. `convertArray` copies the elements (go-ole `ToValueArray`) and keeps no reference, so clearing after conversion is safe. This is the only call site that receives arrays.

## Tests (`internal/agent/wmi/variant_clear_test.go`, real oleaut32)
- A `VT_ARRAY|VT_BSTR` variant converts to `["80","443"]` and is `VT_EMPTY` after `safeVariantClear`. On unfixed code it stays `0x2008`, so the test fails. A second clear is a no-op.
- A by-reference variant is left untouched.
- 50,000 convert+clear reads of a 3-element string array must not grow private bytes by more than 5 MB. Unfixed they grow **12.5-14.7 MB (~300 B per read)**; fixed, **0.1-1.4 MB** of heap noise.

## Host proof
Pending; this PR will be updated with the numbers.
- **Baseline, main@b9c8636:** VM private bytes +1.45 MB/h (13.5 h, r² 0.97); laptop (older build) +2.29 MB/h (20 h).
- **Amplification on the VM (main build, `firewallRules.intervalSeconds` 300 → 60):** running since 19:10Z 2026-09-25.
- **Fixed build:** running on the laptop with UMDH stack tracing, to attribute any remaining native growth.
- **Acceptance:** a 24 h run with a slope under 0.1 MB/h after warm-up on both hosts, then the 72 h soak.

Other leads from the audit are being tested separately, one PR each if confirmed: a new SWbemLocator/ConnectServer per query for non-cimv2 namespaces (~230 per hour), and per-verification catalog/crypt state.

## Evidence so far (2026-09-25)

### Real host: amplification on the VM (main@b9c8636, only `firewallRules.intervalSeconds` 300 → 60)
Private bytes, 1-min samples, 20-min warm-up dropped:

| Build + config | Private-bytes slope |
|---|---|
| main, default config | **+1.45 MB/h** (13.5 h, r² 0.97) |
| main, firewall every 60 s | **+8.8 MB/h ± 0.6** (r² 0.83) |

- 5× the firewall cycles gives 6× the slope, so the firewall collector's array reads dominate the leak.
- The fixed build with the same 60 s config has been running on the VM since 20:14Z; results will follow.

### In-process probe: each collector's real `Collect` cycle run in a loop on the laptop, private bytes after warm-up

| Collector | Unfixed | Fixed |
|---|---|---|
| firewallRules (696 rules, ~9.7 s/cycle) | +5.4 MB / 40 cycles (52-225 KB/cycle → 0.6-2.7 MB/h at 300 s) | −0.9 MB / 40 cycles (flat) |
| defenderState | +1.5 MB / 100 cycles | +0.3 MB, warm-up only |

The same probe found **no per-cycle native growth** (second half of each run within noise, native part = private bytes − Go runtime Sys) in:
- the other 11 poll collectors;
- the process poll, targeted `GetProcessByPID` and owner lookup;
- `WinVerifyTrust` + catalog signature verification (1,000 rounds with the cache cleared);
- the `Win32_ProcessStartTrace` subscription (6,000 real process starts; ~1.4 MB one-time warm-up, then flat);
- new connection per non-cimv2 query (4,000 connections, ~160 B/connection at the margin).

So this PR should account for the whole native slope. Proof will be the 24 h / 72 h runs on both hosts.
