## Why

The 6-hour WMI connection recycle is the mitigation for the long-lived COM/WMI connection memory leak. It silently stopped working with PR #69 (b04fd72, 2026-09-23): `recycleConnection` created the replacement **before** removing the aged connection, and #69 made `createConnection` enforce `MaxConnections`, so on a full pool the replacement was always refused.

Lab evidence, both hosts ~14 h after the last deploy:

```
{"component":"wmi_pool","error":"connection pool exhausted","level":"error","msg":"Failed to create replacement connection"}
```

| | VM | laptop |
|---|---|---|
| error lines / hour after ~6 h uptime | 150 | 105 |
| working set, deploy to +14 h | 34 → 58 MB | 46 → 70 MB |
| Go heap (`Memory stats` alloc_mb) | flat 4–7 MB | flat |

Connections reported `age 13h46m, max_age 6h0m` and were never replaced; the growth is native (COM), not Go.

## What

`checkAndRecycleConnections` recycles **idle** connections only: drain the idle queue, close and unregister aged ones, put the rest back, then create replacements into the freed slots. An aged connection that is in use is recycled on a later health cycle after it is returned. The old `recycleConnection` is removed (it also left the removed connection in the idle queue and type-asserted `*wmiConnection`). A replacement refused because a concurrent `Get` already took the freed slot is debug.

## Verification

- `pool_recycle_test.go`: full pool with two aged + one fresh idle connection → both aged closed once and unregistered, two replacements, pool full and idle, no warning/error; in-use aged connection untouched until returned. **Both tests fail on main's `pool.go`** (`aged connections must be closed once, got 0 / 0`) and pass with the fix.
- `go build ./...`, `go vet`, `go test ./internal/agent/wmi/` (real WMI on this host), `golangci-lint` on the package: clean.
- Lab: deployed to the VM and the laptop with a 72 h soak sampling working set, handles and recycle log lines every 30 min; evidence after the first 6 h cycle added below.
